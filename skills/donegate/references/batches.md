# Batch operations

Use `donegate --repo-root /absolute/repo --json --compact` with `task create-many --file tasks.json` to create a list of normal task definitions. Read returned IDs once. Create a bounded group using `batch create --title NAME --task-id ID --task-id ID --mode auto --rationale REASON`; declare prerequisites with `--dependencies '{"consumer":["prerequisite"]}'`. High-risk groups use `--risk high`; explicit mode overrides need a rationale.

`batch activate ID` binds the branch, `batch start ID` starts members, and `batch submit ID` submits the group. After related implementation, `batch check ID` runs required checks once per shared command in batch mode and reuses valid results; `--force` reruns. Inspect per-task failures and actual executed/reused counts. After real doc inspection use `batch doc-sync ID --result synced --notes REASON`, then `batch done ID`. Failed members are not silently closed.

`batch show ID`, `batch active`, `batch list` and `context` retrieve compact working state. Keep full histories/logs lazy. The agent tools expose equivalent operations; always pass absolute repo_root. A single task activation exits batch mode for that branch. A batch is a development/regression boundary, not a reason to weaken acceptance. Per-task test_commands declare coverage; dependencies and shared fixtures/config must be explicitly scoped. Manual acceptance still requires actual evidence. Use forced regression for changed external state. Historical delivery survives ordinary code changes, while current stale evidence still needs revalidation at delivery boundaries.
